# Markdown 编译器产品想法记录

- 文档状态：讨论稿 v0.1
- 更新时间：2026-09-16
- 当前工作名称：待定
- 参考项目：Nexus-Editor（GitHub 项目介绍，作为竞品和方向参考）

## 0. 当前共识

我们要开发的不是又一个只提供左右分栏预览的 Markdown 输入框，也不是把 Markdown 转成另一种 JSON 文档模型的富文本编辑器。

初步方向是：

> 构建一个以 Markdown 源文本为唯一事实来源、以 AST 为核心中间结构、可以嵌入不同产品的 Markdown 编译与编辑引擎。

这里的“编译”包括解析、诊断、AST 转换、插件处理和目标渲染；编辑器是建立在这个编译核心之上的交互层。

## 1. 对 Nexus-Editor 的产品判断

以下判断来自用户提供的项目介绍，尚未对其源码逐项验证。

### 1.1 它主要是什么

Nexus-Editor 更准确的分类是：

- 一个无头（headless）的 Markdown 编辑器引擎；
- 一个可嵌入其他产品的前端 SDK；
- 一个使用 CodeMirror 6 负责文本编辑、使用 unified/mdast 负责 Markdown 解析和 AST 的组合；
- 一个提供框架绑定、编辑器事件、插件和 Widget 扩展能力的基础设施。

它不是一个面向普通用户直接安装使用的完整笔记软件，也不是单纯的 Markdown 到 HTML 的命令行编译器。

### 1.2 它解决的核心问题

Nexus 的核心判断是：Markdown 文件本身应该是真正的文档，而不是被导入 JSON 编辑器后只保留一份近似内容。

因此它强调：

- Markdown 文本是文档真值；
- AST 是从文本派生出的结构，而不是替代文本的存储格式；
- 编辑和预览可以结合，但不强迫用户进入 WYSIWYG 模式；
- 需要扩展时，扩展应该作用在快捷键、Markdown AST 和 CodeMirror 三个层次；
- 文件 IO、本地优先和 Electron/Tauri 集成应该是重要能力；
- 核心逻辑不绑定某一个 UI 框架。

### 1.3 它面向谁

主要用户不是普通 Markdown 读者，而是需要把 Markdown 编辑能力嵌入自己产品的开发者和团队：

1. **笔记应用开发者**
   - 需要 Markdown 原文存储；
   - 需要内联预览、标题折叠、代码块和表格等交互；
   - 需要本地文件或本地优先能力。

2. **文档 CMS 和知识库开发者**
   - 需要让用户直接编辑 Markdown；
   - 需要自定义提示块、组件、链接和元数据；
   - 需要将 Markdown 继续交给后续发布流程。

3. **静态站点和技术写作工具开发者**
   - 需要编辑器和站点生成器共享 Markdown 语法；
   - 需要主题、代码高亮、目录和扩展语法；
   - 需要批量编译和文件监听。

4. **Markdown 原生的个人知识管理产品开发者**
   - 希望保留用户文件的可迁移性；
   - 不希望数据被锁在某个数据库或 JSON schema 中；
   - 需要链接、标签、嵌入和自定义节点。

5. **LLM 写作工具开发者**
   - 需要让模型生成或修改 Markdown；
   - 需要在文本、AST 和界面组件之间建立稳定映射；
   - 需要保留人工编辑结果，避免模型重写时破坏格式。

### 1.4 它给用户的主要价值

对使用者来说，价值不是“多一个编辑器界面”，而是减少自己实现以下基础设施的成本：

- CodeMirror 6 生命周期和编辑事务；
- Markdown 实时解析；
- AST 节点和编辑器位置之间的映射；
- 内联预览和 Widget；
- 快捷键、斜杠菜单和插件；
- React、Vue、原生 DOM 的绑定；
- 本地文件读写与防抖；
- 编辑器事件和扩展点。

## 2. Nexus-Editor 的产品边界

### 它擅长的方向

- 作为其他应用中的编辑器内核；
- 保留 Markdown 文本；
- 提供类似 Obsidian 的实时内联预览；
- 支持开发者编写扩展；
- 为本地优先应用提供文件 IO 接口；
- 让 React、Vue 和原生 DOM 应用共享一套核心逻辑。

### 从介绍中暂时看不到或尚未明确的方向

以下不是对其能力的否定，而是我们需要重点验证和改进的机会：

- 是否有真正的增量解析，而不是输入后重新处理整份文档；
- Markdown 原文、AST、Widget 和渲染结果之间是否有完整的位置映射；
- 复杂修改是否能够保证格式和空白完全不漂移；
- 多文档依赖、引用、资源和构建过程如何处理；
- 编译错误是否具备文件、行列号、错误码和修复建议；
- 插件的版本兼容、执行顺序、权限和故障隔离是否有明确规范；
- 超大文档、低配置设备和离线环境下的性能；
- 是否提供可靠的 HTML、PDF、DOCX 或其他目标后端；
- 是否有可用于生产环境的可访问性、国际化和安全模型；
- Headless 能力与可直接使用的参考 UI 之间如何平衡。

## 3. 我们可以做得更好的方向

我们不应该只把 Nexus 的功能列表再增加一遍。更好的产品需要在“编译内核的可靠性”和“嵌入产品后的开发体验”上形成明显差异。

### 3.1 把编辑器背后的编译器做成一等公民

建议明确分成四层：

```text
Markdown 源文本
    ↓
解析与诊断
    ↓
带位置信息的 AST / IR
    ↓
转换、插件和依赖分析
    ↓
编辑器视图 / HTML / 静态页面 / 其他后端
```

编辑器只是其中一个消费者。这样未来可以同时支持：

- 交互式编辑；
- 静态 HTML 构建；
- 文档预览；
- LLM 结构化修改；
- 其他输出后端。

### 3.2 保证源文本优先，而不是只宣传“无损”

需要把“无损”写成可测试的产品契约：

- 普通编辑不会把 Markdown 重新序列化；
- AST 只作为派生结构；
- AST 操作通过精确文本补丁应用；
- 保留软换行、空格、引用标识符和用户原有排版；
- 无法安全修改时返回诊断，而不是静默重排源文件；
- 对关键语法提供 round-trip 和位置映射测试。

### 3.3 做好真正的增量编译

目标不是每次输入都重新解析整篇文档，而是：

- 根据编辑事务定位受影响的范围；
- 只更新受影响的 AST 节点和 Widget；
- 把解析放入 Worker，避免阻塞输入；
- 对大型文件使用缓存；
- 输出稳定的性能指标。

### 3.4 建立更清楚的插件模型

建议从一开始区分：

1. **编辑器插件**：快捷键、命令、选择区、事务；
2. **语法插件**：remark/unified 解析、转换和诊断；
3. **渲染插件**：AST 节点到 HTML、Widget 或其他输出；
4. **宿主适配器**：文件、网络、数据库和应用状态。

每层都需要有：

- 版本和兼容范围；
- 执行顺序；
- 输入输出类型；
- 错误处理方式；
- 是否允许修改源文本；
- 测试和调试工具。

### 3.5 提供完整的位置映射和诊断

每个 AST 节点、渲染块和编辑器 Widget 都应能追溯到 Markdown 的源范围：

```text
文档片段 → Markdown offset → 行列号 → AST 节点 → 视图 Widget
```

这样可以支持：

- 点击预览定位源码；
- 错误高亮；
- LLM 精确修改某个节点；
- 结构化重命名和批量更新；
- 更可靠的调试工具。

### 3.6 解决 Headless 产品的上手门槛

完全不提供 UI 会把大量工作转嫁给使用者。可以保留无头核心，同时提供：

- 官方参考主题；
- 可复制的 React、Vue、Vanilla 示例；
- 可访问的默认工具栏和命令面板；
- Electron/Tauri 示例应用；
- 组件级样式变量，而不是强制完整设计系统。

这样既保留自由度，也让用户能够在一天内完成集成。

### 3.7 把本地优先做成可靠的数据层

需要考虑的不只是“提供文件 IO 钩子”，还包括：

- 原子写入；
- 外部文件变更检测；
- 冲突提示；
- 防抖和批量保存；
- 编码和换行符处理；
- 图片、附件和相对路径；
- 离线运行；
- 文件权限和插件安全边界。

## 4. 我们的初步产品定义

### 暂定一句话

> 一个 Markdown 原生的编译与编辑引擎：以源文本为真值，以带位置的 AST 驱动编辑、预览、插件和多目标输出。

### 暂定目标用户

第一阶段优先服务：

- 正在开发笔记应用、文档 CMS、静态站点工具或 LLM 编辑器的开发者；
- 需要 Markdown 文件长期可迁移的团队；
- 不想被 WYSIWYG 文档模型和专有数据格式绑定的产品团队。

### 暂定核心场景

1. 将编辑器嵌入一个本地优先的 Markdown 应用；
2. 在文档 CMS 中提供可扩展的 Markdown 编辑能力；
3. 为静态站点或技术文档提供编辑、预览和构建一体的内核；
4. 让 LLM 对 Markdown 文档进行结构化修改，同时保持用户原有格式。

## 5. 建议的第一版 MVP

### 必须具备

- Markdown 原文作为唯一存储真值；
- CommonMark/GFM 解析；
- 带位置信息的 AST；
- 行列号、错误码和诊断信息；
- 基于 CodeMirror 6 的编辑运行时；
- 可选的内联预览；
- HTML 渲染后端；
- 基础 Widget API；
- 编辑器、语法、渲染三类插件接口；
- Vanilla API 和一个主流框架绑定；
- 大文档性能基准；
- 源文本和位置映射测试。

### 可以推迟

- 多人实时 CRDT 协作；
- 评论和 @提醒；
- 插件市场；
- 多种复杂输出格式；
- 完整所见即所得模式；
- 云端账号和同步；
- 移动端应用。

## 6. 还需要共同决定的问题

1. 我们的第一产品到底是 SDK、桌面应用，还是两者共享的核心？
2. 第一批用户优先是笔记应用开发者、文档工具开发者，还是 LLM 产品开发者？
3. “编译器”是否需要在第一版直接输出 HTML，还是先完成编辑器内核？
4. 我们要保证的 Markdown 范围是 CommonMark/GFM，还是需要尽早支持自定义块、MDX、数学公式和 Mermaid？
5. 我们要优先做 React、Vue、Vanilla 中的哪一个绑定？
6. 我们的第一项明确领先指标是什么：大文档性能、格式保真、插件体验、诊断质量，还是集成速度？
7. 是否需要提供一个可直接使用的官方桌面应用，作为能力展示和真实测试环境？
