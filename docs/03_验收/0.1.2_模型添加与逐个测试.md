# 0.1.2：模型自动加入、逐个测试与流式诊断

日期：2026-09-16。

## 用户确认的需求

1. 设置里点“获取模型”之后，模型直接加入列表，不需要再逐个手动点选。
2. “测试连接”应当按模型逐个测试，每个模型单独给出结果。
3. 前端需要流式输出；用 DeepSeek 模型测试时出现错误，并且客户端闪退。

## 改动

### 获取模型 → 直接加入列表

`获取模型` 现在把服务返回的全部模型合并进模型列表（按 ID 去重，已存在的模型保留用户已设置的能力），并在当前没有选中模型时自动选中第一个。返回结果里的上下文长度（`context_window`、`context_length`、`max_model_len`）会写入新模型的上下文上限，因此新加入的行可以直接使用。提示信息写明本次获取与新增数量。

保存按钮仍然需要点一次：它负责把名称、密钥和模型列表写回 `settings.json`。新增模型不再需要“逐个点选 + 添加模型”两步。

### 测试连接 → 逐个模型

- 模型列表每行新增一个测试按钮，并在行内显示该模型的状态徽标：`测试中` / `可用` / `失败`（悬停可见失败原因与耗时）。
- `测试全部模型` 依次探测每个模型，最后汇总“N 个可用 / M 个失败：模型 · 原因”。
- 遇到配置级失败（鉴权失败、超时、404）立即停止后续测试并注明已跳过数量，避免每个模型都等满超时。
- 页脚 `测试连接` 仍然测试当前模型，并同步该行的状态徽标。

### 流式输出与 DeepSeek

- **探针（测试连接）之前会失败于自身参数**：旧实现固定 `max_tokens: 16` 并携带 `reasoning_effort`。推理模型在真正回答之前就把预算用在推理上，服务返回空正文或直接拒绝，用户看到的就是“测试连接报错”。现在探针预算不低于 256，并在探测时关闭 reasoning effort。
- 只支持流式的服务：缓冲式探针拿不到正文时，自动改用流式重试一次，收到任意 token 即判定可用。
- 仅推理/空输出：流结束但没有正文时，不再留下一个永远无法“应用”的空提案，而是提示“模型没有返回正文（只有推理过程或空内容）”。
- 流式提案头部在生成过程中显示已接收字符数，流式过程可见。
- SSE 响应体在提前退出（取消、探针、流错误）时释放，避免连接残留。
- HTTP 429 映射为 `RATE_LIMITED`，设置页给出限流/额度的中英文提示。
- 模型列表读取上下文长度的字段名扩展到 `context_window`、`context_length`、`max_model_len`。

### 闪退诊断：根因未能复现

本机 `logs/desktop.log` 在用户报告的时间段内没有 `RENDERER_EXIT`、也没有 `UNCAUGHT_EXCEPTION`，说明退出不是 JS 层异常：窗口是干净关闭的（或进程被直接结束）。没有 API Key 无法重现真实 DeepSeek 请求，因此本次只补齐了缺失的证据链，没有声称修好了根因。

新增日志（写入 `logs/desktop.log`，不含密钥、提示词或文档内容）：

| 记录 | 含义 |
| --- | --- |
| `UNHANDLED_REJECTION` / `UNCAUGHT_EXCEPTION`（带消息） | 主进程异常与未处理的 Promise 拒绝 |
| `CHILD_PROCESS_GONE <type> <reason> exit=<code>` | 网络/GPU/工具进程退出，可解释“无 JS 错误却消失” |
| `RENDERER_ERROR <消息>` | 渲染进程 console error（含未捕获的页面错误） |
| `RENDERER_EXIT <reason> exit=<code>` | 渲染进程崩溃（已有，补充退出码） |
| `AI_GENERATE <协议> <主机> <模型>` / `AI_GENERATE_DONE` / `AI_GENERATE_CANCELLED` / `AI_GENERATE_ERROR <code>` | 生成请求的开始与终态 |
| `AI_MODELS_FAILED` / `AI_TEST_FAILED <code> status=<n>` | 模型列表与连接测试的失败 |
| `WINDOW_CLOSED` / `APP_QUIT` | 正常退出路径 |

崩溃复现时，请提供 `logs/desktop.log` 末尾若干行与操作时间，即可区分“渲染进程崩溃 / 子进程退出 / 正常关闭”。

## 追加：模型发现回退、日志同步与一处更正

用户在真实 Key 会话中使用的配置是 `https://api.deepseek.com/anthropic` + `anthropic-messages`。该会话日志显示：

- `AI_GENERATE anthropic-messages api.deepseek.com deepseek-v4-pro` → 14 秒后 `AI_GENERATE_DONE`：真实流式生成成功。
- 两次用户取消各留下一条 `AI_GENERATE_ERROR AI_REQUEST_FAILED`，取消导致的读取中断被当成通用错误上报。
- 之后进程以退出码 0 结束，但**没有** `WINDOW_CLOSED` / `APP_QUIT`：关闭路径的日志用的是异步写，进程随即退出时这两行会丢失（冒烟测试里因为进程多存活一会儿，所以能看到）。

据此追加三项修复：

1. 模型发现（`listModels`）在同源范围内按顺序尝试多个候选路径，全部 404/405 时才报 `MODEL_LIST_UNAVAILABLE`，并把**已尝试的路径**写进错误消息（设置页仍显示中英文友好提示，路径只出现在日志里）。DeepSeek 仍然以文档路径 `/models` 为先，`/v1/models`、`/anthropic/v1/models` 仅作为同源回退；其他服务保持原有首选路径，仅在基础地址不含版本段时追加 `/v1/models`。凭据只在同一 origin 内使用。
2. `logs/desktop.log` 改为**同步写入**，关闭路径的日志不会再丢。
3. 取消（abort）统一映射为 `ABORTED`，不再报成 `AI_REQUEST_FAILED`。

### 更正：日志里那两条 404 不是用户点击导致的

`07:01:17` 的两条 `AI_MODELS_FAILED MODEL_LIST_UNAVAILABLE status=404` 一度被读成“用户点获取模型失败”。日志时间线否定了这一判断：`07:01:14.990` 启动 → `07:01:16.174` 关闭 → `07:01:16.610` 再次启动 → 0.4 秒内出现两条 404，与同日 `06:22:33` 冒烟运行留下的模式完全一致（`settings:smoke` 的本地夹具本来就对 `/v1/models` 返回 404，且会连续点击两次“获取模型”）。真实用户操作是 `07:01:59` 之后的生成请求。因此 DeepSeek 的 `/models` 是否可用仍**没有**实证，本次回退改动属于防御性加固，首选路径未变。
